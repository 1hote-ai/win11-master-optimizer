# Как мы делали прозрачный Open-Source оптимизатор Windows 11: архитектура, безопасность и откат вместо твикеров из 2010-х

*Хаб: Разработка под Windows, Системное администрирование, Open Source, Геймдев*  
*Теги: windows 11, powershell, низкая задержка, dpc latency, msi mode, open source, производительность*

---

Каждый, кто хоть раз играл в соревновательные шутеры вроде CS2, Valorant или Apex Legends, наверняка натыкался на так называемые «паки оптимизации от про-игроков». Как правило, это запароленный архив с файлообменника, внутри которого лежит десяток пожелтевших от времени `.bat` файлов, пара закрытых утилит неизвестного происхождения с детектами на VirusTotal и обещание «+500% FPS БЕЗ ЛАГОВ».

Открываешь такой `.bat` в блокноте — и волосы встают дыбом:
- Команды с синтаксическими ошибками вида `del "$env:SystemRoot\..."`, написанные людьми, не понимающими разницу между переменными cmd и PowerShell.
- Слепое удаление системных веток реестра без возможности восстановления.
- Вырезание Microsoft Store, калькулятора и базовых служб авторизации, из-за чего через неделю Windows Update намертво ломает систему.
- Полное отсутствие логирования и точек восстановления: автор скрипта на серьезных щах пишет в `README.txt`: *«Если что-то сломалось — переустанови винду»*.

Нас категорически не устраивало такое состояние дел. Если инструмент позиционируется как средство тонкой настройки операционной системы для соревновательного гейминга, он должен разрабатываться по стандартам серьезного системного ПО: с модульной архитектурой, чистым исходным кодом, интеграцией с NT-ядром и гарантией отката в один клик.

Так появился проект **Windows 11 Master Optimizer**. В этой статье мы подробно разберем его внутреннее устройство, подводные камни Windows 11 24H2 и покажем, как мы реализовали безопасный откат и работу с системными прерываниями.

## 1. Архитектурный каркас: почему PowerShell и модули

Главная беда любительских скриптов — монолитность и отсутствие типизации. Когда в одном файле на 5000 строк перемешаны твики меню «Пуск», вызовы `netsh` и правки драйверов видеокарты, поддерживать и тестировать такой код невозможно.

Мы разделили проект на ядро-оркестратор (`Win11Optimizer.ps1`) и восемь изолированных модулей (`.psm1`):

```
win11-master-optimizer/
├── Win11Optimizer.ps1             # TUI-интерфейс и CLI-оркестратор
├── Test-Win11Optimizer.ps1        # Автоматический тестовый набор (34 ассерта)
├── Modules/
│   ├── Safety.psm1                # Снимки реестра, VSS точки восстановления и откат
│   ├── GamingLatency.psm1         # MSI Mode, планировщик CPU, Standby RAM, VBS
│   ├── NetworkGaming.psm1         # Алгоритм Нейгла, RSS, TCP стек, DNS Benchmark & DoH
│   ├── GpuDisplay.psm1            # DWM MPO, HAGS, DirectX Windowed, HDCP Killer, очистка кэша
│   ├── Debloat.psm1               # Отключение Recall 24H2, Copilot, Bing, Telemetry
│   ├── SystemUI.psm1              # Меню Windows 10, Проводник, отключение сна USB
│   ├── Diagnostics.psm1           # 26-точечный аудит, Win32 таймер, замер DPC/ISR
│   └── AppInstaller.psm1          # Winget-менеджер для тихого развертывания софта
```

Каждый модуль работает в режиме `Set-StrictMode -Version Latest`, а все функции, модифицирующие систему, обязательно поддерживают параметр `-DryRun`. Пользователь может запустить скрипт с флагом `-DryRun` и увидеть в терминале точный список ключей, параметров и значений, которые будут затронуты, не меняя ни единого байта в реальной системе.

## 2. Безопасность превыше всего: двухуровневый движок отката

Самая сложная инженерная задача при разработке твикера — не применить настройку, а **гарантировать её стопроцентный откат**.

Большинство авторов твикеров просто применяют `.reg` файлы. Но реестр Windows — это не просто таблица ключ-значение. Там важен исходный тип значения (`DWord`, `QWord`, `Binary`, `MultiString`, `ExpandString`), а также факт того, существовал ли параметр изначально или он был создан твикером с нуля.

В модуле `Safety.psm1` мы реализовали двухуровневый механизм защиты:

### Уровень 1: Обход 24-часового лимита Windows System Restore
Windows 10 и 11 содержат скрытое ограничение: по умолчанию служба System Restore не позволяет создавать точки восстановления чаще, чем один раз в 24 часа. Если скрипт просто вызовет `Checkpoint-Computer`, при повторном запуске команда тихо завершится с ошибкой, оставив пользователя без резервной копии.

Мы обошли это ограничение через установку параметра `SystemRestorePointCreationFrequency = 0`:

```powershell
# Обход 24-часового лимита Windows на создание точек восстановления
$srKey = "HKLM:\SOFTWARE\Microsoft\Windows NT\CurrentVersion\SystemRestore"
if (Test-Path $srKey) {
    Set-ItemProperty -Path $srKey -Name "SystemRestorePointCreationFrequency" -Value 0 -Type DWord -Force
}
Checkpoint-Computer -Description $pointDesc -RestorePointType "MODIFY_SETTINGS" -ErrorAction Stop
```

### Уровень 2: Гранулярные JSON-снимки реестра
Перед тем как коснуться любого ключа реестра, функция `Save-RegistrySnapshot` опрашивает целевые пути через .NET `Microsoft.Win32.Registry` и сериализует в JSON:
1. Существовал ли ключ? (`KeyExists`)
2. Существовал ли конкретный именованный параметр? (`ValueExists`)
3. Каково было точное значение? (`Value`)
4. Каков был его исходный тип данных? (`Type` — DWord, Binary, String и т.д.)

При откате (`Restore-RegistrySnapshot`) алгоритм обрабатывает три сценария:
- Если ключа изначально не было — созданный параметр удаляется, а если родительский ключ остался пуст, удаляется и сам созданный подраздел.
- Если ключ был, но параметра в нем не было — удаляется только добавленный параметр.
- Если значение было изменено — восстанавливается точное исходное значение с сохранением типа данных.

Благодаря этому откат не оставляет «мусорных» хвостов в реестре и не повреждает системные структуры.

## 3. Вызов NT-ядра: очистка Standby RAM без сторонних EXE

В играх с большим открытым миром (Tarkov, Rust, Battlefield) игроки часто сталкиваются с периодическими микрофризами. Причина кроется в подсистеме управления памятью Windows.

Windows кэширует прочитанные файлы в так называемый **Standby List** (кэшированная память). Когда приложению требуется новый блок оперативной памяти, а свободного пространства не осталось, диспетчеру памяти приходится на лету вытеснять страницы из Standby List. Этот процесс синхронный и на доли секунды блокирует потоки рендеринга.

Старые гайды советовали скачивать утилиту `EmptyStandbyList.exe`. Но кто знает, что зашито в этот скомпилированный бинарник? Некоторые античиты (например, Riot Vanguard) справедливо относятся к сторонним низкоуровневым процессам с подозрением.

Мы решили эту проблему чисто: скомпилировали нативный C# P/Invoke класс прямо в памяти процесса PowerShell:

```csharp
[DllImport("ntdll.dll")]
public static extern int NtSetSystemInformation(
    int SystemInformationClass, 
    ref int SystemInformation, 
    int SystemInformationLength
);

// SystemMemoryListInformation = 80 (0x50)
// MemoryPurgeStandbyList = 4
// MemoryEmptyWorkingSets = 2
```

Для вызова `NtSetSystemInformation` требуются особые системные привилегии, которых нет даже у стандартного администратора без явной активации. Скрипт запрашивает у локального токена безопасности привилегии `SeProfileSingleProcessPrivilege` и `SeIncreaseQuotaPrivilege` через `advapi32!AdjustTokenPrivileges`, после чего передает команду ядру. Память очищается за 2 миллисекунды без единого внешнего файла на диске.

## 4. Аппаратные прерывания: MSI Mode и фильтрация шины PCI

Большинство периферийных устройств в Windows по умолчанию работают в режиме устаревших линейных прерываний (Line-Based IRQ). В этом режиме видеокарта, сетевая плата и контроллеры материнской платы могут делить одну физическую линию прерываний. Когда во время сетевой перестрелки сетевая карта бомбардирует процессор пакетами, видеодрайвер вынужден ждать в очереди прерываний.

В мониторах задержки вроде LatencyMon это выглядит как огромные пики **DPC Latency** у драйверов `nvlddmkm.sys` или `ndis.sys`.

Перевод устройств в **MSI Mode (Message Signaled Interrupts)** переключает обработку прерываний на прямую запись сообщений в системную память через шину PCI-Express.

Однако слепо включать MSI Mode для всего подряд смертельно опасно. Если включить его на контроллере жесткого диска или мосте чипсета, система может выпасть в BSOD `INACCESSIBLE_BOOT_DEVICE`.

В модуле `GamingLatency.psm1` мы реализовали строгий фильтр Win32 PnP-сущностей:

```powershell
$pnpDevices = Get-CimInstance Win32_PnPEntity | Where-Object { 
    $_.DeviceID -like 'PCI\*' -and (
        $_.PNPClass -in @('Display', 'Net', 'Media') -or 
        ($_.PNPClass -eq 'System' -and $_.Service -in @('HDAudBus', 'HdAudAddService'))
    )
}
```

Скрипт находит только дискретную видеокарту (Nvidia/AMD), сетевой адаптер (Intel/Realtek) и аудиочип, безопасно выставляя для них `MSISupported = 1` и наивысший приоритет прерываний `DevicePriority = 3 (High)`.

## 5. Адаптация под Windows 11 24H2

В свежем обновлении 24H2 Microsoft добавила ряд спорных фоновых сервисов:
1. **AI Recall:** фоновое сохранение снимков рабочего стола для локальной нейросети.
2. **Интеграция Copilot** на панели задач.
3. **Bing Search** внутри локального меню поиска.

Мы добавили полноценное отключение этих механизмов не просто удалением ярлыков, а на уровне групповых политик и компонентов DISM (`Disable-WindowsOptionalFeature -FeatureName "Recall"`). Меню Пуск моментально возвращается к поиску только по локальным файлам на SSD без обращения к серверам Microsoft.
